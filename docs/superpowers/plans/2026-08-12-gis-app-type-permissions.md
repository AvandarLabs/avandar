# GIS `app_type` Permissions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make GIS a first-class permissioned app: a `gis` value in the `app_type` enum, `gis` permission keys, a role-matrix row in workspace settings, a backfill so no existing member loses access, and a guard on `/map`.

**Architecture:** `AppType` is a Postgres enum mirrored by a TypeScript union. Both `matchLiteral` (in `appLabel`) and `satisfies UserAppRolesMatrix` (in the preset matrices) are exhaustive, so adding one union member makes the compiler enumerate every site that needs updating. The database side needs three migrations in a fixed order because Postgres refuses to use a new enum label in the same transaction that added it.

**Tech Stack:** Postgres (Supabase declarative schema + pgTAP), TypeScript, TanStack Router, Mantine, Lingui.

**Spec:** `docs/superpowers/specs/2026-08-12-gis-avamap-design.md` §6. Runs independently of `2026-08-12-gis-avamap-core-refactor.md`; only Task 6 touches a file that plan also touches.

---

## Required skill

**`supabase-declarative-schema` is MANDATORY for Tasks 1-3.** Load it before editing any SQL. Its non-negotiables: declarative SQL lives in `supabase/schemas/NN.<name>.sql`, and migrations are generated with `supabase db diff` rather than hand-written, with two documented exceptions this plan relies on:

1. **DML (`insert`/`update`/`delete`) is never captured by `db diff`**, so the backfill is a hand-written migration.
2. **Enum label additions** need `alter type ... add value`, and Postgres error `55P04` means a new label cannot be _used_ in the same transaction that added it. `supabase/migrations/20260504000010_add_xlsx_file_source_type_enum_value.sql` is the in-repo precedent for handling this with a dedicated migration.

## Migration order (do not deviate)

| Order | File                                                        | Contents                                                    | Why separate                                                        |
| ----- | ----------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------- |
| 1     | `<ts>_add_gis_app_type_enum_value.sql` (hand-written)       | `alter type public.app_type add value if not exists 'gis';` | The label must be committed before anything references it (`55P04`) |
| 2     | `<ts>_gis_role_group_seeding.sql` (generated by `db diff`)  | replaced `util__seed_builtin_role_groups_for_workspace`     | Function body references `'gis'::public.app_type`                   |
| 3     | `<ts>_backfill_gis_role_group_app_roles.sql` (hand-written) | DML backfill for existing workspaces and groups             | `db diff` never emits DML                                           |

## Decisions this plan locks in

- **Permission keys** mirror the `dashboards` shape: viewer gets `gis__can_view_map`; editor adds `gis__can_edit_map` and `gis__can_create_map`; admin adds `gis__can_manage_maps`.
- **Backfill rule: mirror each role group's `dashboards` role.** A group with `dashboards = editor` gets `gis = editor`. A group with **no** `dashboards` row gets **no** `gis` row, because a group that was never granted a visualization app should not silently gain one. Maps are a visualization surface, so `dashboards` is the closest existing analogue, and mirroring beats defaulting everyone to `viewer`.
- **`resource_type` is not extended here.** Adding `map` to `public.resource_type` only means something once a `maps` table exists to share, which is Wave A. This plan is app-level roles only.

## Task 3: Backfill `gis` roles for existing workspaces

Without this, `UserAppRolesMatrix` reads a missing row as "no access" and every current member loses the GIS app the moment the enum ships.

**Files:**

- Create: `supabase/migrations/<timestamp>_backfill_gis_role_group_app_roles.sql`

- [ ] **Step 1: Create the migration**

```bash
supabase migration new backfill_gis_role_group_app_roles
```

- [ ] **Step 2: Write the backfill**

```sql
-- Backfills `gis` rows in role_group_app_roles for role groups that predate the
-- `gis` app_type. Without this, `UserAppRolesMatrix` reads the missing row as
-- "no access" and existing members lose the GIS app.
--
-- Built-in groups are re-seeded through the seeding helper, which is idempotent.
-- Custom groups mirror their `dashboards` role, because maps are a
-- visualization surface and `dashboards` is its closest existing analogue. A
-- group with no `dashboards` row deliberately gets no `gis` row: it was never
-- granted a visualization app and must not gain one silently.

-- Built-in role groups: the seeding helper now includes `gis` and does nothing
-- to rows that already exist.
do $$
declare
  v_workspace_id uuid;
begin
  for v_workspace_id in
    select id from public.workspaces
  loop
    perform public.util__seed_builtin_role_groups_for_workspace (v_workspace_id);
  end loop;
end;
$$;

-- Custom (non-built-in) role groups: mirror the group's dashboards role.
insert into
  public.role_group_app_roles (
    role_group_id,
    app,
    role
  )
select
  dashboards_role.role_group_id,
  'gis'::public.app_type,
  dashboards_role.role
from
  public.role_group_app_roles dashboards_role
  join public.role_groups rg on rg.id = dashboards_role.role_group_id
where
  dashboards_role.app = 'dashboards'::public.app_type and
  not rg.is_builtin
on conflict (
  role_group_id,
  app
) do nothing;
```

- [ ] **Step 3: Apply and verify the invariant holds**

Run: `pnpm db:apply-migrations`
Expected: applies cleanly.

Run this against the local database:

```sql
select count(*) as groups_with_dashboards_but_no_gis
from public.role_group_app_roles dashboards_role
where dashboards_role.app = 'dashboards'
  and not exists (
    select 1 from public.role_group_app_roles gis_role
    where gis_role.role_group_id = dashboards_role.role_group_id
      and gis_role.app = 'gis'
  );
```

Expected: `0`.

- [ ] **Step 4: Commit**

```bash
git add supabase/migrations
git commit -m "feat(permissions): backfill gis role rows for existing role groups"
```
