# Internationalization (Lingui)

User-facing copy is translated with [Lingui](https://lingui.dev). Messages are
collected at build time by `lingui extract`, which **statically** scans source
for the Lingui macros (`` t`…` ``, `` msg`…` ``, `<Trans>`, `Plural`, …). That
static analysis is the source of the most common i18n bug in this repo, so the
rules below exist to keep every string extractable.

## Macros are recognized lexically, at their own call site

`lingui extract` only treats `` t`…` `` / `` msg`…` `` / `<Trans>` as a message
when the macro identifier is the one bound by the macro import (or the macro
`useLingui()`) in the **same lexical scope**. The extractor does not follow a
translation function across a function boundary.

## Never pass the translation function as a parameter

The `t` returned by `useLingui()` (and any tagged-template translate function) is
a runtime value. If you pass it into another function and call it there, the
extractor cannot see those calls: the strings are never added to the catalogs and
stay untranslated in every non-English locale. English still renders (it is the
source text), which is exactly what makes this bug easy to miss.

```ts
// BAD: nothing inside buildLabel is extracted.
type TranslateFn = ReturnType<typeof useLingui>["t"];
function buildLabel(kind: string, t: TranslateFn): string {
  return kind === "num" ? t`Number` : t`Text`;
}
// caller
const { t } = useLingui();
buildLabel(kind, t); // the t`…` calls inside buildLabel are invisible to extract
```

The same applies to threading `t` into any helper (`buildX(…, t)`), a local
`type TranslateFn = …`, or a parameter named `translate` / `translateFn`.

## Do this instead

### Option A (preferred for runtime-selected strings): `msg` + `i18n._`

Define the messages with the `msg` macro (which **is** statically extracted) and
resolve them at runtime with `i18n._`. Thread the reactive `i18n` from
`useLingui()` so the label updates on locale change.

```ts
import { msg } from "@lingui/core/macro";
import type { I18n } from "@lingui/core";

function buildLabel(kind: string, i18n: I18n): string {
  return i18n._(kind === "num" ? msg`Number` : msg`Text`);
}
// caller
const { i18n } = useLingui();
buildLabel(kind, i18n);
```

### Option B: keep the `` t`…` `` calls in the macro scope

If the strings are static, call `` t`…` `` directly in the component/hook where
`t` came from `useLingui()`, rather than in a helper that receives `t`.

## Passing `i18n` is fine; passing `t` is not

Threading `i18n` and calling `` i18n._(msg`…`) `` is correct: the extractable
part is the `msg` macro, which stays at its own call site. The rule is
specifically about not relocating a **macro** call (`` t`…` ``) out of its
lexical scope.

## Verify

After adding user-facing strings, run `pnpm i18n:extract` and confirm your file
appears as a `#:` reference in `src/i18n/locales/en/messages.po` and your strings
are present. `pnpm i18n:check` (extract + `git diff --exit-code`) is the CI gate.
